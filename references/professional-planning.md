# 专业方法驱动的两轮拆解

需要进一步理解专业拆解时按需读取；首次规划优先遵循 planning.md 的阶段边界。用户最终审阅一份整合后的方案；中间检索与粗拆由宿主完成。简单改写、格式转换等任务保留必要步骤即可。

## 第一轮：识别任务和方法需求

读取材料结构与少量样本后确定用户要理解、决定或完成的事情，提取对象、范围、约束、材料已有的证据和待回答问题；确认前不计算新的业务结论。暂不固定完整节点或报告目录。材料已说明的内容直接采用；追问仅限会改变方法或范围的关键缺口。

分别核对业务方法与文件制作能力。专业方法应提供适用条件、判断步骤、重点项目选择、异常处理或检验要求。只有“分析数据、撰写报告”等描述时，继续查看必要参考和示例；仍不足则按 discovery.md 外搜。文件操作能力与业务方法分别核对。材料已有足够规则和模板时可直接采用适配的制作技能；新增专业技能须能填补具体判断缺口。

专业任务按 [能力选择](capability-selection.md) 在 capability_needs 中统一记录方法覆盖；制作技能无法填补的方法缺口须保留检索结果并用deferred等待解决；核心缺口解决后才执行；新策略不提供专业原生降级。

## 第二轮：根据方法和本次材料重新拆解

选出主要方法，结合材料确定本次重要问题、职责边界和完成标准。候选来源的声誉、星数和评测用于初筛，不能替代实际方法审阅。企业制度、适用口径与用户目标约束方法使用；冲突会改变结论时说明具体取舍。多个技能以主要业务流程组织，辅助技能承接计算、取证或制作，保留必要前置与检查。

每个模块写清：具体问题、方法来源、输入输出、关键约束和完成标准。问题可以在一个模块中成组委托，保留专业技能的重点筛选与深入调查能力。方法可以带来拆分、合并、重排和补充核验。节点数按实际依赖确定；一个节点可以承担多个分析项。

以下是编译后的结构，首次规划填写业务草案即可；无需手工维护这些字段：

- requirements：用户目的、明确约束和完成标准。
- content_outline：分析问题或具体内容。title 写问题；claim 写已有依据支持的判断，尚未分析时写待验证问题；points 写选题依据、方法和证据缺口；sources 指向实际材料与方法位置；acceptance 写证据和核验标准。
- nodes：输入输出、执行顺序、分工与 review 检查，通过 outline_ids 关联具体问题。
- 采用 Skill 的方法时将原文与本次流程登记到 skills；编译器生成材料引用与 binding。宿主按该 Skill 的完整方法执行并留存记录。
- open_questions：尚无法解决且影响分析的缺口。执行条件与方法依据分别说明，读取文档不代表调用已就绪。

规划时形成具体问题和分析安排。依赖计算、检索或调查的结论留到执行阶段；呈现任务默认列主题范围与关键证据，正文、细纲和分镜在执行阶段形成。用户明确要求先审阅细纲时再展开。

## 从实际 Skill 生成本次执行安排

读取选定 Skill 的入口及与本任务有关的参考、示例、脚本。提取它解决的问题、适用条件、必要输入、重点对象选择依据、步骤与条件分支、交付约定及验证方式。阅读深度以足够决定本次工作为准，忽略无关资源。把读取位置和判断写入候选 evidence，将本次采用方式写入 decision.application，沿用现有字段。

把用户目标、材料中的具体线索和这些方法相互对照，生成本次问题、节点和检查：

- 任务问题决定需要哪些专业方法；方法帮助发现用户没有用专业术语表达的重点。必要输入不足时，缩小结论范围或指出会改变方案的缺口。
- 成熟流程整体调用；无需将技能内部步骤复写进方案。专业 Skill 负责其必要步骤、分支和检查，方案只提出本次约束与跨模块交接。会改变目标、范围或外部操作授权的分支回到用户决定。
- 每个模块的调用说明由最新 plan.json 生成，携带本模块的需求、方法依据、材料、具体问题、输入输出和验收；使用 `sos.py brief plan.json --node N1`。宿主仍须读取实际 Skill，并使用其准确调用入口。该命令不调用模型或创建额外 agent。
- 从用户标准、材料约束、专业 Skill 的验证规则分别推导 checks 与内容 acceptance。检查写清对象、方法、位置、期望结果；可以是行为测试、推导复核、来源比对、抽样审查、现场确认或文件渲染。具备可执行检查器时先记录覆盖标准，确认执行后再按 native-checks.md 留存结果。
- 尚无独立标准时标出待验证假设；避免让执行结果反过来降低验收要求。原生检查覆盖有限时保留针对本任务的内容审阅。新增方法发现明显遗漏时，更新受影响内容、依赖和检查后再交付方案。

提示词和检查内容随任务变化。固定协议只负责需求覆盖、引用一致、保存版本、授权范围、依赖与证据。一次检查命令通过只说明该检查覆盖的条件成立。跨步骤需要的产物应明确交接，执行时从 run.json 读取通过验证的实际文件路径。

## 两个结构示意

以下为虚构示意，方法和数值须由每次任务的真实材料支持，不能作为预设业务规则。

**经营分析**：用户提供本期与上期汇总、分项明细，想理解变化。第一轮识别比较对象、时间口径和解释需求；读取适用分析方法后，将“重点变化如何形成”写成具体分析项。若汇总显示增长而某些分项下降，计划明确核对汇总与明细关系、分别量化贡献、调查抵消项，并列出解释原因仍缺的业务证据。验收要求各项贡献与总变化核对，原因解释有独立依据，未解部分保留待核实。仅有汇总表时，计划说明可计算范围及补充材料的用途。

**供应商方案比较**：用户材料规定内网部署、上线期限和首年预算。读取适用比较方法后，先核对硬性条件及证据，再对满足条件的方案比较成本与交付范围；含糊报价列为澄清项。方案写清费用包含项、维护费、期限依据及其如何影响选择。权重来自用户或业务规则，缺失时提供情景比较建议。验收核对每项推荐理由与原报价、条件证据的关系。

两类任务都可以产出报告，但分析顺序与检查依据由任务问题决定。研究任务同样需要问题与证据路径；诊断任务明确现象、影响与证据要求，由专业技能提出和验证候选原因；汇报任务明确主题、受众和关键证据，由专业技能组织细纲。

## 交付前与执行后的覆盖检查

1. 逐项对照用户目的、材料中的重要疑点、适用方法要求，检查是否有负责节点和相应内容。合理排除的分析说明适用性原因，避免堆叠无关指标。
2. 查看采用方法支持了哪些问题、判断步骤或检查，包含正确沿用的安排。只写技能名、制作文件和最后排查时，返回第二轮修订。
3. 检查方法所需数据是否具备，来源是否读过，缺口是否会阻碍承诺的结论。仍不足时交付有边界的方案和具体缺口。
4. 执行后逐项检查回答、依据、限制和未解问题。原因不明时保留假设；不得用术语、图表数量或字段齐全代替专业判断。

脚本可核对结构与引用，专业覆盖需要宿主审阅。真实试用重点记录遗漏的重要问题、步骤适配、结论依据和用户返工；案例通过不推导为所有专业任务均可靠。
