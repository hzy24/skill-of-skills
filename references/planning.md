# 首次规划：选择专业能力，交付任务方案

`<skill>` 是本技能目录；`<task>` 是本任务独立可写目录。技能安装目录只读；元景优先使用 /sessions/<本次会话>/sos-task。init 会把共享目录纠正到当前会话，拒绝跨会话目录和旧状态。始终使用 init 返回的 task_dir，材料保留原位置。重复 init 保留预算与状态。用户后续另行交办新任务时，用新目录 init --new-request 记录该条原话。

工具输出先给 phase、status 和下一步动作，再给所需内容。长字段列在 paged_fields，按 view_command 加 `--field 字段名` 分页读取，随后沿 next_page_command 继续；原始记录完整保留。返回丢失或解析异常时运行 `status`，读取 last_result_command。读取记录不耗检索额度，避免为查看结果重新搜索。

## 1. 输入画像

```sh
python <skill>/scripts/flow.py <task> init --goal '用户原始需求' --inputs <材料路径...>
```

这是读取附件内容的第一步，无需另写 head、pandas 或 CSV 脚本。无附件时省略 --inputs。init 提供表头、三行样本、类型、缺失计数和日期范围。根据这些信息判断任务类型与能力要求。材料关系、指标、归因、建议和成品内容交给执行阶段。结构画像仍无法确定日期或类型时，可调用 `probe 1 列名 date_range` 或 `probe 1 列名 types`；XLSX 用 --sheet 指定表名，合计两项。需要确认类别含义时可用 `probe 1 列名 labels`，最多返回20项取值，不返回频次。文档用 `material 1` 查看目录，再用 `material 1 --section 2` 阅读相关章节；补读最多四个相关章节，重复读取复用缓存；仅核对选型所需的原文，保持业务计算与成品撰写在执行阶段。PDF 读取复用环境中的 pdftotext 或 pypdf；缺少解析器时记录实际读取状态，避免把未读材料写成已核验。

## 2. 发现与选型

```sh
python <skill>/scripts/flow.py <task> search '业务对象短词' '专业岗位短词'
python <skill>/scripts/flow.py <task> inspect <搜索返回的slug>
```

从需求映射到专业领域，再用中文短概念检索腾讯 SkillHub。结果偏泛时加 --category 优先展示相关分类；零命中时换中文同义词。分类可按任务选 data-analysis、professional、business-ops、it-ops-security 等。原始目标保留价格与保修、负荷与时长等关系；市场查询每项只写一个 2–8 字中文概念，优先 2–6 字。程序拆开连接词、去掉分析等动作尾词；无效词在联网前纠正。各查询先均衡召回；业务检索三轮共至多十二次请求，每次展示本轮优先的 12 项候选，分类用于排序。接口 score 是检索信号，能力质量由原文判断。“主管带的人”可映射为管理幅度、组织设计。结果不合适时换同义词或上位概念。优先使用“具体业务问题 + 专业岗位/领域”两类词，例如分别传入“工单”“客服运营”，或“重复报销”“财务审计”；数据分析、生成报告等通用动作不代替专业领域。找出能完成本次工作的候选即停止检索。已读到直接契合的方法时，额外候选只用于解决明确不足；评分或下载量更高不构成改选理由。

核读实际用途、方法与运行前提后选型；中文检索词无需在方法或列名中重复出现。普通字段改名、多表整理及必要指标推导交由专业 Skill 处理。确实缺少材料、制度或外部系统访问时，在方案约束中说明其影响。

选择顺序：任务与专业方法契合 → 运行条件可满足 → 来源与交付质量 → 平台评分、下载量。只提供 API 操作的接口不能自动等同于分析方法；说明费用、账号和系统依赖；以实际方法为依据。

已安装能力登记：

```sh
python <skill>/scripts/flow.py <task> local <实际SKILL.md路径>
python <skill>/scripts/flow.py <task> local <文件制作SKILL.md路径> --role support
```

业务核心采用相关专业 Skill，用途画像依据原文。统计或数据分析方法承担核心工作时使用下述 method 路径；纯制图、格式制作及接口操作仍按其职责使用。未分类用途按 purpose_options 用 --purpose 选择编号并说明职责。文件制作工具可承担配套交付；纯排版或格式转换可由制作工具主导。最多核读三个可读取的核心候选；失败来源另用替补额度，总获取次数最多六次，失败来源不重复下载。检索与核读按动作计数，每次获取独立超时。本地配套制作另有三个登记名额。该入口登记真实文件制作能力，返回后可直接写路线；分析方法继续使用原候选编号。下载的方法文档及其副本保持外部来源和安装提案，不登记为已安装。原文指向必要方法文档时，用 `resource <候选编号> <清单内相对路径>` 补读，合计两份。来源与安装提案自动登记，完整安装需授权；`section <候选编号> <章节序号或完整标题>` 可读取关键章节；序号与 methods 一致，错误参数不扣额度，同一章节重复读取复用原文。

对每个已核读的核心候选作一次选型判断，比较它解决的实际问题和用户原始需求。默认委托完整方法，随后按路线划分阶段；选型无需填写 JSON：

```sh
python <skill>/scripts/flow.py <task> assess <候选编号> --fit suitable --coverage task \
  --reason '该方法怎样直接完成用户原始需求；选择它的具体理由'
python <skill>/scripts/flow.py <task> assess <其他候选编号> --fit unsuitable --reason '实际方法与所需工作存在的区别'
```

仅取部分能力时，添加 `--method 1 --method 3`，或使用完整标题；逗号、顿号及带空格的斜线也可分隔多个标题。`methods <候选编号>` 返回完整编号目录；无法匹配时 assess 直接返回可选项，不改变原有判断。淘汰候选只需理由，不需要章节。

task 表示所选方法直接解决具体业务问题。只有专用检索没有命中，或已核读候选的方法确实不适合时，才扩大到同领域通用方法：search ... --level domain，然后 assess ... --coverage domain。有多个具体任务候选时至少比较两项实际方法；只有一项时核读该项，成功检索零命中时保留检索记录。程序保留专用检索和淘汰依据；已有合适的任务方法时禁止换成领域通用方法。领域方法须说明如何完成需求。来源故障不代表方法不适配。

### 可迁移方法的选用

当业务候选的方法未覆盖当前问题，或某个统计、数据分析、运筹方法更适合所需证据时，在规划内做一次有依据的方法比较。先完成业务检索，对已核读候选记录取舍；有召回结果时核读最相关业务候选，成功检索零命中时保留记录。无需穷尽市场或为了数量额外淘汰候选。已有直接契合的方法时说明新方法解决的具体不足；技能名称更通用、评分更高均不足以改选。

```sh
python <skill>/scripts/flow.py <task> search '相关性分析' '统计分析' --level method --category data-analysis
python <skill>/scripts/flow.py <task> inspect <实际候选slug>
python <skill>/scripts/flow.py <task> assess <候选编号> --fit suitable --coverage method \
  --method 1 --scope '该技能负责的具体问题与结果' \
  --limit '未覆盖的业务判断，以及由材料制度、其他技能或人工复核处理的方式' \
  --reason '相较已核读业务候选，此方法适合当前问题的具体依据'
```

方法查询使用 2–12 字中文方法名，保留“分析”等方法名称中的词。此路径增加一轮检索与两个可读候选名额；总计最多四轮、十六次请求、五个可读候选，含失败替补最多获取八次。已安装分析技能可直接登记评估。失败终态不开放此路径。搜索轮次与核读次数分别计算：搜索结束后有未读候选且核读额度可用时，程序返回 inspection_required 及已有候选；重复方法检索复用此前结果，不新增请求。

scope、limit 和 reason 自动进入 plan.json、HTML 技能详情与执行委托。方案保留它是可迁移方法的事实，明确能交付什么，以及哪些结论需要额外业务依据。核心目标仍需有可行安排；不能只写“有局限”然后照常承诺所有判断。原生脚本只在确认后作为所选 Skill 的实现手段，不能取代技能绑定。程序核验来源与字段，宿主判断实际适用性。

只处理已核读候选；单候选无需陪选。材料或运行限制用 --limit 记录。预算不改变适配判断。

## 3. 按专业方法组织任务路线

选型后判断：用户需要回答哪些不同问题？哪些结果要先完成，哪些可以并行？哪些阶段需要用户单独修改？据此组织阶段。同一 Skill 可负责多阶段，各阶段可输出多个文件。单一改写、转换可保留一个阶段。按专业方法中的业务步骤划分，避免套用“分析 → 报告 → 检查”固定模板。

选型结束会返回当前任务的路线模板及实际候选编号；也可运行：

```sh
python <skill>/scripts/flow.py <task> route-template
```

按当前任务填写 route.json，依据可独立审阅或交接的结果增删阶段。

- reason：划分阶段的业务依据。简单任务单阶段说明为何足够。
- stages：每项保留 title / candidate / question / method / outputs / checks / after。candidate 使用返回的实际编号；question 是待回答的问题；method 解释所选方法在本阶段的用途；outputs 与 checks 是文本列表；after 引用上游阶段标题，独立阶段用 []。
- deliver：引用 outputs 中最终要交付用户的文件名，其他文件供阶段交接。文件名只在 outputs 登记，说明和检查中沿用同一名称。
- 制作阶段引用 local --role support 返回的候选编号，通过 after 接收专业结果。程序自动沿用 production 角色，无需再次 assess 或填写 role；已有显式 role 仍接受校验。一个 Skill 可承担多个阶段，阶段内的算法、阈值核实、计算与内容生成由专业技能负责。

```sh
python <skill>/scripts/flow.py <task> route <task>/route.json
```

格式有误时，工具一次列出路径及问题；可用 Edit 修正 route.json 或 review_file 的对应位置后重新提交。context_file、来源及协议状态由程序维护。语义不确定的候选、文件和依赖由宿主确认。登记成功返回两个独立文件：

- context_file：只读审阅上下文，包含阶段问题、所选方法原文、输入、交接成果和已声明的范围。
- review_file：简短判断文件；路径由程序绑定当前任务与来源版本，使用工具返回的完整路径。

阅读 context_file，在 review_file 填写各阶段 need、verdict、reason。例如：

```json
{"items":[{"need":"need-1","verdict":"pass","reason":"方法提供所需的负荷与时效比较；附件包含人员及时间字段。结论用于识别运营变化，具体计算与建议在执行阶段完成。"}]}
```

按实际阶段逐项判断。reason 简述该阶段如何服务原始目标、方法如何支持它、材料前提是否成立以及结论范围；无需重复抄写任务全文。需要额外说明时可选填 input_basis、limits。pass 表示核读后适用；fail 表示具体不适配；unverified 表示依据尚未核读。

运行返回的 review_command 提交。方法原文、来源哈希和保护字段均由程序维护，不写入判断文件。校验一次列出所有错误位置；按提示修正判断即可。来源或路线变更时，程序返回当前文件路径，复用仍然有效的阶段判断。重复 route 会恢复只读上下文，保留本版未提交的判断。业务计算与成品内容留给用户确认后的专业执行。

审阅发现问题时，修改对应阶段后再次 route。补选技能用 `reselect '阶段标题' --reason '具体不适配原因'`，保留其他阶段与原预算，再提交路线。程序复用未变化阶段的真实审阅，不把候选选中或来源存在当作阶段适配通过。

新任务使用 route/review，旧任务的 assign/produce 保持兼容。

## 4. 发布与交付

```sh
python <skill>/scripts/flow.py <task> publish
```

publish 生成 plan.json 和可编辑 plan.html，并返回 next_tool。按该动作交付两个文件，将附件工具实际返回的路径交给 finish：

```sh
python <skill>/scripts/flow.py <task> finish --files <实际HTML路径> <实际JSON路径>
```

finish 原子核对最新 JSON、HTML 和附件版本，从同一成果与安装清单生成 `final_reply`。返回 `terminal: true, dispatch: final_reply_only` 即本轮结束；下一条消息仅发送该字段的完整正文。不要重新总结阶段、技能、成果或确认方式。正常路径不传 --reply，旧任务保持兼容。

规划失败返回固定终态并退出 0，表示控制器已处理失败；业务结果仍为 planning_failed。诊断、预算与候选保留在任务目录，执行确认不能解锁。

文件、附件与收尾分别登记；`.sos-terminal.json` 绑定交付版本。真实运行审计核对终态后调用和聊天正文。用户保存页面后，执行读取最新 plan.json；安装与执行授权始终按实际用户指令及最新提案判定。
