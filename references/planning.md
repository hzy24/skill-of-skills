# 首次规划：选择专业能力，交付任务方案

`<skill>` 是本技能目录；`<task>` 是本任务独立可写目录。技能安装目录只读；元景优先使用 /sessions/<本次会话>/sos-task。init 会把共享目录纠正到当前会话，拒绝跨会话目录和旧状态。首次 init 后始终使用返回的 task_dir，材料保留原位置。重新 init 会返回原任务，不清空预算或失败状态。用户在后续消息中另行交办新任务时，才在新目录 init 并附 `--new-request '用户该条新交办原话'`，原记录保留；本轮失败、换措辞、换目录均不构成新交办。

## 1. 输入画像

```sh
python <skill>/scripts/flow.py <task> init --goal '用户原始需求' --inputs <材料路径...>
```

这是读取附件内容的第一步，无需另写 head、pandas 或 CSV 脚本。无附件时省略 --inputs。init 提供表头、三行样本、类型、缺失计数和日期范围。根据这些信息判断任务类型与能力要求。材料关系、指标、归因、建议和成品内容交给执行阶段。结构画像仍无法确定日期或类型时，可调用 `probe 1 列名 date_range` 或 `probe 1 列名 types`；XLSX 用 --sheet 指定表名，合计两项。

## 2. 发现与选型

```sh
python <skill>/scripts/flow.py <task> search '业务对象短词' '专业岗位短词'
python <skill>/scripts/flow.py <task> inspect <搜索返回的slug>
```

从需求映射到专业领域，再用中文短概念检索腾讯 SkillHub。结果偏泛时加 --category 优先展示相关分类；零命中时换中文同义词。分类可选 data-analysis（数据分析）、professional（行业专业）、business-ops（商业运营）、it-ops-security（IT 运维）、office-efficiency（办公效率）、education（教育）、dev-programming（开发编程）、knowledge-management（知识管理）、design-media（设计）、content-creation（内容创作）、ai-agent（智能体）、life-service（生活服务）。原始目标保留价格与保修、负荷与时长等关系；市场查询每项只写一个 2–8 字中文概念，优先 2–6 字。程序拆开连接词、去掉分析等动作尾词；超长整句在联网前返回改词提示，不消耗检索预算。各查询先均衡召回；三轮共至多十二次请求，每词通过腾讯 /api/v1/search 获取最多 50 个候选，每次响应上限 2 MiB，复用缓存；只展示本轮查询优先的 12 条简要候选；优先展示本轮标题与用途命中的候选，再参考接口相关性顺序；缺少词项匹配的热门推荐标记为需要核读，历史候选单独标识。category 是本地排序偏好，不会把发布在其他分类的专业技能删掉。搜索接口 score 表示检索排序信号，不作为能力质量评分。例如日常说法“主管带的人”可映射为管理幅度、组织设计、人力资源。结果不合适时换同义词或上位专业概念。优先使用“具体业务问题 + 专业岗位/领域”两类词，例如分别传入“工单”“客服运营”，或“重复报销”“财务审计”；数据分析、生成报告等通用动作不代替专业领域。找出能完成本次工作的候选即停止检索。已读到直接契合的方法时，额外候选只用于解决明确不足；评分或下载量更高不构成改选理由。

关键词负责召回与排序。核读实际 Skill 的用途、方法、输入类型和运行前提，判断哪一个最适合；中文检索词无需在英文原文、每个方法章节或输入列名中重复出现。普通字段改名、多表整理及必要指标推导交由专业 Skill 处理。确实缺少材料、制度或外部系统访问时，在方案约束中说明其影响。

选择顺序：任务与专业方法契合 → 运行条件可满足 → 来源与交付质量 → 平台评分、下载量。只提供 API 操作的接口不能自动等同于分析方法；收费、账号、外部系统依赖要在选型时说明。目录介绍是候选线索，实际方法原文是选型依据。评分与下载量保留平台原始含义。

已安装能力登记：

```sh
python <skill>/scripts/flow.py <task> local <实际SKILL.md路径>
python <skill>/scripts/flow.py <task> local <文件制作SKILL.md路径> --role support
```

业务核心必须有相关专业 Skill。用途画像读取原文；通用可视化、统计、接口操作不能因名字陌生或 suitable 声明就变成领域方法。未分类用途时 assess 返回 purpose_options；核读后添加 --purpose 编号，reason 说明其负责的业务判断。程序提取对应原文，无需抄写或翻译。该分支支持未收录的新专业，原文绑定不代替适配判断。文件制作工具可承担配套交付；纯排版或格式转换可由制作工具主导。最多核读三个可读取的核心候选；失败来源另用替补额度，总获取次数最多六次，失败来源不重复下载。检索与核读按动作计数，模型思考时间不消耗下载时限；每个候选的实际网络获取仍有独立超时。本地配套制作另有三个登记名额。原文指向必要方法文档时，用 `resource <候选编号> <清单内相对路径>` 补读，合计两份。方法来源与安装提案自动登记，完整下载等待用户批准具体提案。核读输出保留用途限制和方法目录；`section <编号> <章节编号>` 可读取被截断的关键章节。

对每个已核读的核心候选作一次选型判断，比较它解决的实际问题和用户原始需求。选型默认保留完整方法来源，程序绑定原始技能与代表性章节；随后通过任务路线划分阶段范围。选型时无需先挑章节或填写 JSON：

```sh
python <skill>/scripts/flow.py <task> assess <候选编号> --fit suitable --coverage task \
  --reason '该方法怎样直接完成用户原始需求；选择它的具体理由'
python <skill>/scripts/flow.py <task> assess <其他候选编号> --fit unsuitable --reason '实际方法与所需工作存在的区别'
```

仅取部分能力时，添加 `--method 1 --method 3`，或使用完整标题；逗号、顿号及带空格的斜线也可分隔多个标题。`methods <候选编号>` 返回完整编号目录；无法匹配时 assess 直接返回可选项，不改变原有判断。淘汰候选只需理由，不需要章节。

task 表示所选方法直接解决具体业务问题。只有专用检索没有命中，或已核读候选的方法确实不适合时，才扩大到同领域通用方法：search ... --level domain，然后 assess ... --coverage domain。有多个具体任务候选时至少比较两项实际方法；只有一项时核读该项，成功检索零命中时保留检索记录。程序保留专用检索和淘汰依据；已有合适的任务方法时禁止换成领域通用方法。领域方法仍须解释怎样完成原始业务需求。下载或解析失败应修复来源，不代表市场缺少方法，也不授予原生分析或跨领域通用统计的替代权限。

只处理已核读的候选，单候选无需额外搜索陪选。必要材料或运行限制用 --limit 记录。范围相邻但无法回答核心问题的候选要淘汰；核读预算不改变这一判断。程序核对来源与职责绑定，适配判断由 Agent 负责。

## 3. 按专业方法组织任务路线

选型后判断：用户需要回答哪些不同问题？哪些结果要先完成，哪些可以并行？哪些阶段需要用户单独修改？据此组织阶段。同一个 Skill 可以承担多个阶段，一个阶段也可以输出多个文件。阶段数量由实际工作决定；单一改写、转换等任务可保留一个阶段。按专业方法中的业务步骤划分，避免套用“分析 → 报告 → 检查”固定模板。

用 Write 在 `<task>/route.json` 一次写下路线，再通过 route 登记。reason 说明阶段划分依据；单阶段说明为什么一个阶段足够。每个阶段给出待回答的问题、所选方法如何用于该阶段、结果文件与完成标准。计算、阈值选择和结论留到执行。下面以已选定服务运营技能的工单任务为例；实际阶段按当前技能的方法和用户需求组织：

```json
{
  "reason": "按服务运营方法先对照人员接单负荷，再结合处理时效诊断瓶颈；两阶段复用同一专业技能。",
  "deliver": ["服务改进建议.md", "人员月度负荷.csv"],
  "stages": [
    {"title": "人员接单负荷", "candidate": "核读返回的编号", "question": "哪些人员的月度接单量持续增加？", "method": "采用服务运营技能的工单量指标，按人员和月份比较。", "outputs": ["人员月度负荷.csv"], "checks": ["人员与月份范围可追溯到工单记录"], "after": []},
    {"title": "处理时效与瓶颈", "candidate": "同一编号", "question": "接单量增加的人员处理时间是否变化，哪些措施有数据支持？", "method": "采用服务运营技能的时效指标和诊断方法，对照上游负荷结果。", "outputs": ["服务改进建议.md"], "checks": ["解释与建议对应可核查依据"], "after": ["人员接单负荷"]}
  ]
}
```

```sh
python <skill>/scripts/flow.py <task> route <task>/route.json
```

- `deliver` 列出最终需要交付用户的文件；其余 outputs 为供后续阶段复用的中间结果。中间结果也可以列入 deliver 作为用户需要的底稿。一个文件只登记一次；文件名之外的说明写入 question/checks。
- `after` 引用上游阶段标题，程序生成依赖和输入清单；无需手写节点 ID、安装提案或方法引用。独立阶段用空列表。同一技能的方法原文、安装与选型记录共用，阶段范围分别保留。
- `method` 简述已核读方法在本阶段的用途。保留专业技能的前置和验证要求，执行时由技能安排内部操作。
- 专业阶段默认 `role=core`。需要文件制作能力时，先 `local <实际技能路径> --role support`，相应阶段填写 `role=production` 并通过 after 接收专业结果。纯制作任务可由制作技能负责核心阶段。
- 工具会一次校验完整路线，再登记；失败时保留原草案，不留下半条路线。发布前可以修改同一 route.json 再提交，确认方案后通过 HTML 编辑。

查看返回的阶段清单，核对原始交办、专业问题、阶段结果与最终交付的对应关系。复杂工作若只剩一个“完成整件事”的模块，应根据所选方法展开业务阶段。多个卡片重复相同问题、只改标题，不能体现有效拆解。

旧任务继续支持 assign/produce；新任务用 route 登记完整路线。需要把已登记文件转交制作技能时，可使用 `produce <制作候选编号> --takeover 文件名 --check 要求`。专业检索在路线登记后关闭，避免重新选型循环。

## 4. 发布与交付

```sh
python <skill>/scripts/flow.py <task> publish
```

publish 生成 plan.json 和可编辑 plan.html，并返回 next_tool。按该动作交付两个文件，将附件工具实际返回的路径交给 finish：

```sh
python <skill>/scripts/flow.py <task> finish --files <实际HTML路径> <实际JSON路径> --reply '准备发送的完整回复'
```

publish 同时返回 final_reply_template，内容来自最终节点与交付物；可以直接将模板传给 --reply。finish 核对文件与拟发送回复，出现额外技能、文件承诺或遗漏授权时，以最新 plan.json 生成的正文自动替换，并保留差异记录。返回 JSON 中的 final_reply 是唯一需要发送的正文；终端附带的环境日志不属于回复。下一条消息原样发送 final_reply，结束本轮等待用户审阅；交付正文包含方案版本、成果与具体安装授权；业务问题、实际 Skill 与检查要求在 HTML 中查看。聊天不另写业务摘要或追加交付承诺。附件交付、完成记录和确认均由执行入口核验。HTML 保存后，执行读取最新 JSON。

发布关闭本轮编排。后续调用只返回当前交付动作或终态；恢复交付用 `status`。程序生成失败时保存诊断，原样发送 user_message 并结束。本轮不另列原生分析方案、不建议制作工具代替核心专业能力、不新建目录重试。旧版已保存任务继续使用其原有提交协议。控制器内部字段、脚本和状态由程序维护。

用户确认后读取[执行协议](execution.md)；保存服务恢复按[部署恢复](yuanjing-deployment.md)。

规划允许用 Write 写 route.json；每次终端调用只运行一条上述 flow.py 命令（允许先 cd 到工作目录），保留原始返回，不拼接业务脚本、head/tail 或其他命令。状态和内部文件由控制器维护。测试与支持宿主可用 scripts/planning_audit.py 核查真实调用与最终回复；这是独立调用审计，安装 Skill 本身不注册宿主级工具拦截。
